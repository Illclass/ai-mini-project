# 평가셋 관리

두 파일은 같은 `POST /rag-query/evaluations` 엔드포인트에 경로를 지정해 각각 실행합니다. 인증, 요청·응답 형식, 케이스별 진단 로그는 같습니다.

| 파일 | 용도 | 케이스 수 | API의 split |
|---|---|---:|---|
| `evaluation.json` | 개발 중 반복 실행, 프롬프트·검색·검증 변경의 회귀 확인 | 40 | `test` |
| `validation.json` | 개발 평가와 다른 질문 의도로 구성한 최종 검증 후보 | 40 | `validation` |

개발 평가:

```json
{"dataset_path": "eval/datasets/evaluation.json"}
```

최종 검증:

```json
{"dataset_path": "eval/datasets/validation.json"}
```

경로는 서버의 `rag-service/eval` 기준입니다. `datasets/evaluation.json`과 해당 파일의 절대 경로도 사용할 수 있습니다. 예전 `eval/diagnostic_cases_40.json`은 API에서 `evaluation.json`으로 연결하며, 중복된 실제 파일을 유지하지 않습니다.

## 케이스와 채점

각 케이스의 `request`와 `expected`는 질문·기대 결과 쌍으로 함께 관리합니다. 채점 대상은 상태코드, answered/held/error, handoff, 출처 수·문서, 보류 사유, 지정 문구입니다. 답변 본문 전체의 사실성이나 법률 적합성을 자동 판정하는 평가는 아닙니다.

`evaluation.json`은 기존 40개 케이스의 ID·질문·기대값을 보존했습니다. T/V로 시작하는 기존 ID도 보존했지만 모두 개발 평가용 `test`입니다. ID 접두사로 실행 대상을 판단하지 마세요.

새 검증셋 ID는 `VAL01`~`VAL40`으로 구분해 두 파일의 결과를 비교할 때 기존 케이스와 혼동하지 않도록 했습니다.

`validation.json`은 기존 질문의 번역본이나 단순 바꿔쓰기를 재사용하지 않도록 질문 의도를 구분했습니다. 동일 질문 가족의 번역본은 한 파일 안에만 둡니다. RAG가 검색하는 원문 문서는 두 평가에서 공유할 수 있으며, 새 문서에 대한 일반화 평가를 의미하지는 않습니다.

검증셋 40행은 새 도메인 질문 8가족의 언어별 변형 32개와 요청 형식 오류 8개입니다. 도메인 질문은 제품 식별 정보, 법령 제8·9조, 미등록·불일치 제품에 집중합니다. 번역 질문은 같은 의미 단위로 묶어 해석하며, 이 40행이 서로 독립적인 40개 질문 의도이거나 전체 화학안전·법령 범위를 대표하는 것은 아닙니다. 기대값은 목표 동작이므로 현재 코드의 미지원이나 회귀가 있으면 실패로 표시됩니다.

## 변경 원칙

1. 개발 중 확인하고 고치는 케이스는 `evaluation.json`에서 관리합니다.
2. 최종 검증셋은 고정해 관리합니다. 최종 검증 결과를 보며 반복 수정하면 그 셋도 개발 평가로 사용한 것이므로, 새 최종 검증 질문이 필요합니다.
3. 검증셋 내용을 수정할 때는 변경 사유와 고정 지문 테스트를 함께 검토합니다. `version`은 파일 형식 버전이며 현재는 `1`을 유지합니다. 테스트만 통과시키기 위해 기대값을 실제 오동작에 맞추지 않습니다.
4. 실제 실행은 LLM 호출을 포함합니다. 코드 회귀 테스트는 가짜 검색·LLM으로 배치 동작과 파일 구성을 확인합니다.

현재 데이터셋 로더는 `version: 1` 형식을 사용합니다. 내용 개정 이력은 커밋·변경 사유로 남기고, 형식 버전을 올릴 때는 로더와 함께 변경합니다.
